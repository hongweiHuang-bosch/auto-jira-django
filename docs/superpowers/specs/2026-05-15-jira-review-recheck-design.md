# Jira 详情页复核功能设计

- 文档日期：2026-05-15
- 主题：在 Jira Analyzer 的单票详情页里增加“复核”流程，使用固定 few-shot 错例样本再次让模型检查结论，并在复核失败时阻止 Jira 回填，直到人工修改分析结果并保存
- 范围标签：**复核闸门 + 错例样本库**

## 1. 背景与现状

### 1.1 当前链路

当前单票链路已经具备以下能力：

- 详情页：`jira-analyzer-web/src/views/GroupDetail/ProcessedIssueDetail.vue`
- 票结果：`analyzer.models.IssueProcessTask` / `IssueProcessResult`
- Jira 原票元信息：
  - `analyzer.services.jira_issue_payload.build_jira_issue_payload`
  - `legacy_core.jira_utils.JiraClient`
- 当前模型分析提示词来源：
  - `legacy_core/config_map.py`
  - `analyzer.services.issue_analysis_service`
  - `legacy_core/ai_client_by_langchain.py`

当前系统已经能：

- 对票进行分析并输出 `reply_text`
- 展示历史处理结果
- 读取 Jira 评论
- 读取 Jira transitions
- 对 Jira 票执行分配和流转

但是目前没有以下能力：

- 在 Jira 回填前增加一层复核
- 将错例沉淀成可复用的 few-shot 样本
- 在复核失败时阻止 Jira 回填，直到人工修改分析结果并保存后才恢复回填能力
- 将“易错票”做成可持久化标记，并用于后续自动纠错

### 1.2 关键约束

用户已经明确了以下业务约束：

- 不更换公司提供的 `32b qwen` 主模型
- 复核发生在“分析结果已显示、Jira 回填之前”
- 复核失败时，直接阻止 Jira 回填，只有人工修改分析结果并点击保存之后才可继续回填 Jira
- 错例只保存精简内容，不保存完整原始大样本
- 错例样本全局共享，但可按 `role_index` 过滤
- 复核时固定拼接 3 条 few-shot 错例样本
- 复核提示词主体仍保存在 `config_map.py`

### 1.3 现有数据复用判断

现有 `IssueProcessResult` 已保存：

- `reply_text`
- `raw_signals`
- `can_trace_image`
- `can_trace_image_url`
- `result_status`
- `error_message`

这些字段足以支撑复核输入中的“模型结论”和部分证据，但不够保存“复核结果”和“错例样本状态”，因此需要最小扩展。

## 2. 目标

### 2.1 业务目标

给单票详情页增加复核按钮，在 Jira 回填前再次让模型检查当前结论是否正确。复核通过后才能回填 Jira；复核失败后阻止回填，并把该票标记为易错票，直到人工修改分析结果并点击保存后，才重新允许回填。

### 2.2 成功标准

- 单票详情页可以触发复核
- 复核结果能明确显示“复核正确”或“模型分析出现问题，建议手动分析”
- 复核失败后 Jira 回填不可继续，直到人工修改分析结果并保存
- 错例样本可持久化
- 后续复核会自动拼接最近 3 条相关 few-shot 错例样本
- few-shot 样本能按 `role_index` 过滤

## 3. 方案对比

### 方案 A：只加复核按钮，不做错例样本库

流程：分析结果生成后，用户点复核，后端调用模型检查；成功放行，失败阻止回填。

优点：

- 改动最小
- 上线最快

缺点：

- 复核能力不会随着历史错例积累而变强
- 不能形成长期纠偏闭环

### 方案 B：复核按钮 + 错例样本库 + 固定 few-shot

流程：分析结果后触发复核；复核失败写入错例样本库；后续复核先按 `role_index` 取 3 条错例作为 few-shot 拼入 prompt；复核失败时阻止 Jira 回填，直到人工修改分析结果并保存后才恢复。

优点：

- 满足当前需求核心
- 形成稳定的错例积累和持续纠偏机制
- 实现复杂度和收益平衡最好

缺点：

- 需要新增持久化结构
- 需要管理样本筛选与 prompt 长度

### 方案 C：复核按钮 + 错例样本库 + 检索召回 + 自动纠错闭环

流程：在方案 B 基础上，再引入相似度检索、样本管理页面、人工修正工作台。

优点：

- 最完整
- 可扩展性最好

缺点：

- 范围明显更大
- 会把当前功能演化成一个独立知识库产品

### 结论

采用 **方案 B**。它满足当前业务目标，同时不会把系统拆到过度复杂的程度。

## 4. 设计方案

### 4.1 流程概览

单票详情页的推荐流程：

1. 分析结果展示完成
2. 用户点击“复核”
3. 后端收集当前票的复核输入
4. 拼接 `config_map.py` 中的复核 prompt
5. 追加固定 3 条 few-shot 错例样本
6. 调用公司提供的 `32b qwen` 做二次判断
7. 返回 `PASS` 或 `FAIL`
8. `PASS` 时允许 Jira 回填
9. `FAIL` 时阻止 Jira 回填，并生成易错标记；若人工修改分析结果并保存，则复核状态失效并重新进入待复核状态

### 4.2 复核输入

复核时输入给模型的内容固定包含：

- Jira 评论
- 信号
- QNX 日志摘要
- Android 日志摘要
- cantrace 解析输出
- 当前模型给出的结论 `reply_text`
- 固定 3 条 few-shot 错例样本

样本应只保留“错例与标准答案”，不存完整原始大日志。

### 4.3 复核结果定义

复核输出建议统一为以下状态：

- `PASS`：当前结论正确，允许 Jira 回填
- `FAIL`：当前结论错误，阻止 Jira 回填，直到人工修改分析结果并保存

辅助信息：

- `review_reason`：模型解释
- `reviewed_at`：复核时间
- `review_model`：复核所用模型标识

### 4.4 错例样本结构

建议新增一张轻量样本表，字段最小化为：

- `role_index`
- `issue_key`
- `incorrect_conclusion`
- `correct_conclusion`
- `error_reason`
- `review_status`
- `created_at`
- `updated_at`

说明：

- 全局共享依赖于这张表是全局可查询的
- 按规则组过滤依赖 `role_index`
- few-shot 只取最近 3 条同规则组样本

### 4.5 few-shot 拼接策略

复核 prompt 由两部分组成：

1. `config_map.py` 中的复核模板
2. 从样本库中取出的最近 3 条错例样本

拼接规则：

- 优先按当前 `role_index` 过滤
- 只取 `PASS/FAIL` 已确认的错例样本
- 按 `updated_at` 或 `created_at` 倒序
- 固定 3 条，不做动态扩展

### 4.6 回填拦截

Jira 回填接口必须先检查复核状态：

- 若复核通过，继续回填
- 若复核失败或尚未复核，直接拒绝
- 前端不得绕过该限制

这条拦截应落在后端，而不是只靠前端按钮禁用。

## 5. 后端接口设计

### 5.1 复核接口

建议新增：

- `POST /api/rule-groups/<role_index>/processed-issues/<issue_key>/review/`

职责：

- 收集复核输入
- 取最近 3 条 few-shot 样本
- 调用模型
- 保存复核结果
- 若失败则创建或更新错例样本

返回：

- `review_status`
- `review_reason`
- `allow_jira_comment`
- `few_shot_count`
- `reviewed_at`

### 5.2 复核上下文接口

建议新增：

- `GET /api/rule-groups/<role_index>/processed-issues/<issue_key>/review-context/`

职责：

- 返回当前票复核时会用到的材料预览
- 便于前端查看 prompt 组成

### 5.3 Jira 回填拦截

现有回填接口不改 URL，但要增加复核校验：

- 未通过复核，返回 400 或 409
- 已通过复核，允许继续执行 Jira 回填
- 若分析结果已被人工修改并保存但尚未重新复核，也返回阻断错误，提示先复核再回填

## 6. 前端设计

### 6.1 页面位置

复核按钮放在单票详情页中，建议和 Jira 面板放在同一区域，靠近回填按钮。

### 6.2 交互状态

页面至少展示以下状态：

- `未复核`
- `复核中`
- `复核正确`
- `模型分析出现问题，建议手动分析`
- `已人工修改，待重新复核`

### 6.3 按钮状态

- 复核未通过前，Jira 回填按钮禁用
- 复核通过后，才允许回填
- 复核失败后显示阻断原因，并提示“先人工修改分析结果并保存”

### 6.4 样本预览

不是必须，但建议后续预留一个折叠区域，能看到：

- 本次复核输入摘要
- few-shot 样本数量
- 当前规则组命中的样本

## 7. 数据持久化与知识闭环

### 7.1 写入时机

只有在复核失败时，才写入错例样本。

### 7.2 写入内容

仅保存精简字段：

- 票号
- 规则组
- 模型错误结论
- 正确结论
- 错误原因

### 7.3 读取时机

每次复核前，从样本库中读取最近 3 条同规则组错例，拼入 prompt。

### 7.4 不做的事

- 不保存完整原始日志全文到错例库
- 不做复杂向量检索
- 不做样本管理后台页面
- 不做自动强制纠错流程

## 8. 风险与处理

### 8.1 prompt 过长

风险：当前票材料很长，few-shot 再叠加会超上下文。

处理：

- 输入内容只保留摘要版
- few-shot 固定 3 条
- 若超长，优先截断日志类内容，而不是截断结论和样本

### 8.2 误阻止回填

风险：复核服务异常导致 Jira 回填被误拦。

处理：

- 明确区分“复核失败”与“复核服务异常”
- 复核服务异常时返回单独错误态，不直接标记为失败样本

### 8.3 样本污染

风险：错误的错例被写入后，后续 few-shot 反而误导模型。

处理：

- 默认由复核失败结果自动写入正式样本池，保持闭环简单可用
- 为避免长期污染，后续可再扩展“停用样本”或“人工复核样本”状态
- 当前版本不引入人工确认门槛，避免错例无法及时沉淀

## 9. 测试计划

### 9.1 后端测试

覆盖：

- 复核接口返回 `PASS/FAIL`
- few-shot 固定 3 条
- 复核失败会写入错例样本
- 回填接口在未复核、复核失败或人工修改后未重新复核时拒绝
- 复核服务异常时不污染已有历史详情数据

### 9.2 前端测试

覆盖：

- 复核按钮展示和状态切换
- 复核结果展示
- Jira 回填按钮禁用/启用
- 错误提示展示
- 人工修改分析结果并保存后，复核状态失效

### 9.3 回归测试

覆盖：

- 现有规则组详情页不受影响
- 单票历史详情页仍可正常打开
- Jira 原网页链接和 Jira 评论功能不回归

## 10. 结论

本次实现建议采用：

- 复核在回填前触发
- 复核失败直接阻止 Jira 回填，直到人工修改分析结果并保存后重新复核
- 错例只保留精简样本
- 样本全局共享但按 `role_index` 过滤
- 每次复核固定拼接 3 条 few-shot

这套方案能在不更换主模型的前提下，形成“复核 - 错例沉淀 - few-shot 纠偏”的闭环。
